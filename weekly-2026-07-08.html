InjectSync：从补规则到 dependency graph

这周的重点不是再补一条 mail，而是把“哪条指令依赖哪个物理资源、这条依赖能不能安全 lowering、最终 token 是否配平”变成统一模型。

MR !450 merged Dependency graph Midend contract Token ledger

为什么旧 InjectSync 必须重构

  • 旧逻辑主要靠 phase 内局部 heuristic 和 fallback 修 case；loop、branch、CT/front-end、DMA RMW、weight slab 一叠加，就容易“修一个、漏一个”。
  • VCS 通常只能暴露最终 raw mismatch、hang 或 mailbox leftover，不能直接告诉我们是资源没建模、candidate 没生成、admission 不安全，还是 token 放错频率。
  • 硬件 mailbox 只有 sender / receiver counter，没有 op、address、resource、slab tag；同一 channel 上多个资源同时 outstanding 时，不能靠“多发一条 mail”赌语义正确。
  • 后端降到 ZeusLow 后只看到 SSA/BReg 和最终配置链，无法可靠反推出中端已知的 L2 base/size、DMA window offset、weight DRAM slab provenance。

这轮重构的核心

  • 每条指令先进入 InstructionEffect，显式列出 read/write/effect resource。
  • 在 typed resource 上生成 linear、cross-block、loop-carried candidate edge。
  • candidate 不能直接 lowering，必须经过 admission；只有 admitted edge 才进入 dependency-graph。
  • Phase 3 / Phase 4 lowering 只消费 admitted graph edge，展开成 token plan / lowering plan。
  • TokenLedger 最后检查 static、loop frequency、branch / CFG path balance，确保 kernel exit mailbox 回到空状态。
  • report 的价值是审计这条链路；核心不是“打印 report”，而是 graph + admission + token plan 真的接管 lowering。
跨层 contract 为什么不是纯后端问题 当前口径
zeus.l2_region_base / zeus.l2_region_size_bytes 不同 SSA BReg 可能落在同一段物理 L2；后端只看 use-def 判不出完整 overlap。 ZeusHighToZeusLow 把 AddressAllocation 的 base/size 保留到 BRegSetAddrOp；当前 same-block RAW / ordered WAR 可消费，Phase 3/4 仍保守。
zeus.dma_window_offset 同一 AReg base 下 DMA 可能访问不同静态 window；动态 byte offset 不能伪装成一个静态 key。 静态 create_fmap_desc.offset 下传到 DMA op；当前主要用于 shadow candidate / 诊断，不全面 admitted lowering。
zeus.weight_dram_slab LW / DMA store 写 weight DRAM，PE / DMA load 读同一 slab，SSA usage 不同但物理资源相同。 用 canonical slab id 建 store-to-read RAW；same-block bucket 可按 resource-aware key 去重，复杂条件路径仍 fallback。
aliasBreg、nan_safe_fill、CT/front-end snapshot CT/config/descriptor 是 front-end snapshot 语义，不等同普通 L2 backend done dependency。 nan-safe fill 的静态 L2 LD/DT -> VP Phase 3 RAW 已准入；复杂 CT mixed lifecycle 继续显示 fallback reason。

PIK / PIC：明确哪些 kernel 受影响，哪些需要继续扫

这条线的核心是 PE weight descriptor 的合法性：不是 raw PIK 一个字段，而是 RTL predecode 后 effective PIK/PIC 的起点对齐。

MR !425 open RTL contract Transferred to midend

问题背景

  • RTL predecode 中，WMode[1] == 1 的 V-cache storage mode 会交换 raw PIK / raw PIC 后再送给 PE，因此软件不能只检查字段名。
  • effective PIK 对齐要求：INT4 需要 256 对齐，INT8 / FP8 / BF16 需要 128 对齐。
  • effective PIC 对齐要求：BF16 需要 64 对齐，INT4 / INT8 / FP8 需要 128 对齐。
  • normal、kcache、vcache 只要最终由 PE_CONV 通过 weight BReg 读取，都要满足这组约束。

处理策略

  • compiler 侧在 CreateWeightDesc 对 normal weight path 做静态 fail-loud，避免非法 descriptor 静默进入后端。
  • simulator PR 17 负责 runtime fail-loud，并补齐 normal / kcache / vcache 的 effective PIK/PIC 检查。
  • kernel 侧按 retile、layout padding、合并 PE dot 或 LW scratch staging 迁移，不再依赖 sub-align PE weight 起点。
  • 这组约束、已知风险 kernel 和 owner 检查清单已经整理后转给中端继续推进。
